# Relay 简要和解读怎么写？

以下写法依照[项目手册的文章风格](../../docs/product-handbook.md#文章风格)。

- 审读时单独打开一份简要或解读，检查首段能否交代对象和眼下的问题。删去「本节介绍」「这一节有几处修复」「其余见各章」这类导读句。
- 简要也按意思分段。一个主要意思写成一段，话题或读者动作变了就空一行。短而集中的简要可以是一段，句子换行由阅读页处理。
- 把功能名放进一次具体操作里。写清「你做了什么 → 工具怎样响应」，把改变结果的条件放在同一句或紧接的一句。假设场景用「比如」「如果」引入。

## 现实同构

使用场景让读者看到会发生什么。读者还需要理解机制时，从熟悉的现实关系里挑一个小例子，例如交接、排队或多人分工。让读者看清例子里的角色和动作分别对应文中的什么，再接回这项机制为什么有用。只借用能对应的部分，产品的条件和结果以原文为准。

## 视觉锚点

简要和解读都用粗体突出读者扫读时要找的动作、选项和关键结果。优先标短语。遇到多个选项、步骤或条件分岔，用一张短图把关系摆在一起，再用正文交代场景和细节。

## Unicode 图

- 分支用 `├─`、`└─`；流程和因果用 `→`、`↓`。只有原文或明确解释支持的关系才连线，不把相关性画成因果。
- 正文负责讲清场景、例子和必要条件；Unicode 图负责展示步骤、对照或对应关系。用正文建立直觉，再用图标出关键关系。
- 每张图只解释一个关系，节点用短语。用粗体标出读者应先扫到的关键节点。补充说明写在图外，省去图和正文的逐项复述。
- 跨节链接放在能说清两节关系的句子里，链接文字指出读者会看到什么。相邻章节也可链接，先看这条关系是否值得标出。
- 文章来源使用阅读页提供的来源入口。稿内链接用于补充具体出处或关联内容。
- 图中的例子、条件和结论应可追溯到原文；补充的说明不能伪装成原文陈述。

Relay 页面保留正文换行。`**粗体**` 用蓝色，行内代码用绿色，`[文字](URL)` 显示为可点击的下划线链接，行首 `>` 显示为有色竖线引用。Unicode 图直接写在正文里，使用真实换行，避免代码围栏和 Markdown 标题。

真实案例是 [processed.json](../content/relay-demo/processed.json) 的 `c0034`：对照“涉及数据库就触发”和“限定到迁移工作”的条件，解释普通查询为什么可能误触发迁移技能。原始语境位于 [source.md](../content/relay-demo/source.md) 的 `c0034`。
